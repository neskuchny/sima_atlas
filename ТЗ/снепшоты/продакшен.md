Да. Тогда правильный дизайн такой: не строить “AI, который каждый раз думает заново”. Это будет дорого, медленно и нестабильно.
Нужно строить производственную систему корпоративной памяти, где AI используется точечно: для извлечения смысла, обновления памяти, планирования поиска и финального ответа. Всё остальное должно делать обычное инженерное хранилище: Postgres, граф, векторы, индексы, очереди, кеши, асинхронные пайплайны.
Главная формула:
Не “загружаем всю компанию в контекст модели”,
а строим компактную, обновляемую модель компании,
которая умеет быстро найти нужный фрагмент памяти.


1. Какой должна быть система в продакшене
Я бы описал целевую систему так:
Company Memory OS
Это не чат-бот и не RAG. Это слой памяти компании, который:
асинхронно обрабатывает все встречи, документы и события;
сохраняет первоисточники;
извлекает факты, сущности, решения, задачи, риски, связи;
обновляет снэпшоты и граф;
строит процессное понимание;
хранит историю изменений;
быстро отвечает на вопросы через планировщик поиска;
становится лучше с каждой встречей;
не тратит миллионы токенов на каждый вопрос;
масштабируется на тысячи и десятки тысяч встреч.
Важно: обучение системы происходит не через дообучение LLM после каждой встречи, а через обновление структурированной памяти: снэпшотов, графа, фактов, таймлайнов, процессов и retrieval-стратегий.

2. Главный production-принцип
Система должна быть построена по принципу:
LLM expensive and slow.
Memory structures cheap and fast.

То есть:
LLM не должен каждый раз читать всё;
LLM не должен сам “держать компанию в голове”;
LLM не должен быть единственным источником логики;
LLM должен работать поверх подготовленной памяти.
В продакшене основной интеллект должен жить в таких слоях:
Postgres / metadata / state
+ Vector search
+ Graph relations
+ Search index
+ Snapshot memory
+ Process memory
+ Retrieval planner
+ LLM only where needed

4. Основная идея: разделить “дорогое понимание” и “дешёвое использование”
После каждой встречи система может потратить немного ресурсов асинхронно, чтобы потом отвечать быстро.
После встречи
Можно асинхронно сделать:
транскрипт
→ summary
→ извлечение фактов
→ извлечение сущностей
→ обновление снэпшотов
→ обновление графа
→ обновление процессов
→ запись истории изменений

Это происходит не в момент пользовательского вопроса.
Во время вопроса
Система делает быстро:
вопрос
→ intent
→ нужные сущности
→ маршрут поиска
→ 3–20 релевантных объектов памяти
→ ответ

То есть query-time должен быть лёгким.

5. Какие хранилища нужны
Для production-ready версии я бы не начинал с тяжёлого enterprise-графа и сложной ML-инфраструктуры. Лучше начать с прагматичного стека.
Базовый стек

- источники
- встречи
- снэпшоты
- версии снэпшотов
- факты
- связи
- задачи
- решения
- права доступа
- tenant isolation

pgvector или Qdrant
- dense embeddings
- sparse / keyword-like retrieval
- vector search по чанкам, снэпшотам, фактам

OpenSearch / Meilisearch / PostgreSQL full-text
- keyword search
- фильтры
- exact match
- имена людей, клиентов, продуктов

Redis
- кеши
- session memory
- hot snapshots
- rate limits
- retrieval cache

Object Storage
- оригинальные транскрипты
- документы
- аудио / видео
- вложения

Queue / Event Bus
- Kafka / Redpanda / NATS / RabbitMQ

Workflow Orchestrator

- долгие пайплайны

Postgres + pgvector хороши для раннего production, потому что позволяют хранить векторы рядом с обычными данными; pgvector прямо позиционируется как vector similarity search внутри Postgres. (GitHub) Для более тяжёлого поиска можно вынести retrieval в Qdrant: у него есть hybrid queries, sparse + dense векторы и RRF-подобное объединение результатов. (qdrant.tech)

6. Что выбрать: pgvector или Qdrant
Для MVP / первых клиентов
Я бы начал с:
PostgreSQL + pgvector + full-text search

Почему:
меньше инфраструктуры;
проще деплой;
проще транзакционность;
проще связать embeddings с metadata;
проще multi-tenant;
быстрее сделать production.
Для масштаба
Когда будет много клиентов, большие объёмы и нужен быстрый hybrid retrieval:
PostgreSQL + Qdrant

Postgres остаётся system of record.
Qdrant становится retrieval engine.
Практическая рекомендация
0–1000 встреч: Postgres + pgvector достаточно
1000–10000 встреч: Postgres + pgvector всё ещё может хватить при нормальных индексах
10000+ встреч / много клиентов / high QPS: Postgres + Qdrant

Но важно: 10 000 встреч — это не страшный масштаб, если не читать их моделью. Это нормальный масштаб для БД и search index.

7. Как сделать систему дешёвой по токенам
Главное: никогда не отправлять в LLM больше, чем нужно.
Query-time budget
Для обычного вопроса:
1. Intent classification: 300–800 токенов
2. Entity lookup: без LLM или маленькая модель
3. Retrieval: без LLM
4. Rerank: маленькая модель / cross-encoder / cheap LLM
5. Answer context: 3–15 чанков + 2–5 снэпшотов
6. Final answer: 4k–20k токенов входа, редко больше

Не 1M токенов.
Не весь граф.
Не все встречи.
Ingestion-time budget
На встречу можно потратить больше, потому что это async:
1. summary встречи
2. extraction фактов
3. extraction задач
4. extraction решений
5. entity resolution
6. snapshot update

Но это тоже надо делать каскадно, а не одной большой моделью.

8. Модельная стратегия
Не надо использовать одну большую модель для всего.
Нужен model cascade.
Уровень 1. Маленькая дешёвая модель
Для:

определения intent
извлечения простых сущностей
маркировки темы
роутинга
простого summary

Варианты:
Qwen 3 4B / 8B
Gemini Flash Lite
локальная маленькая модель

Уровень 2. Средняя быстрая модель
Для:
extraction facts
entity resolution
snapshot update draft
relationship extraction
query planning
answer synthesis

Варианты:
Gemini 3 Flash
Qwen3-30B-A3B
Qwen3-32B
Qwen3-Next-80B-A3B

Gemini 3 Flash Preview сейчас указан в официальной документации Google как модель с входным контекстом 1,048,576 токенов, выходом до 65,536 токенов, поддержкой structured outputs, function calling, caching и Batch API; цена в Gemini 3 Developer Guide указана как $0.50 / $3 за 1M input/output tokens для gemini-3-flash-preview. (Google AI for Developers) Это удобно как внешний быстрый provider, но для production надо учитывать, что это preview-модель и версионировать провайдера.
Для локального стека Qwen: публичные model cards сейчас показывают Qwen3-30B-A3B с native 32,768 context и до 131,072 с YaRN, а Qwen3-30B-A3B-Instruct-2507 — с native 262,144 context; Qwen3-32B также указывается с 32,768 native и до 131,072 с YaRN. (Hugging Face) Для inference локальных моделей можно использовать vLLM: он предоставляет OpenAI-compatible HTTP server. (docs.vllm.ai)
Уровень 3. Сильная модель только для тяжёлых случаев
Для:
сложный анализ
конфликты
стратегический ответ
длинная встреча целиком
deep reasoning

Это не default path.

11. Почему не стоит сразу строить на чистом LightRAG
LightRAG как идея полезен: он совмещает graph structures с retrieval и делает dual-level retrieval для low-level и high-level knowledge discovery. (lightrag.github.io) В репозитории LightRAG также есть сервер, Web UI, API, поддержка PostgreSQL как all-in-one storage и Neo4j для graph storage. (GitHub)
Но для production SaaS я бы использовал LightRAG не как “весь продукт”, а как референсный подход.
Почему:
вам нужен свой multi-tenant model;
свои права доступа;
свои события памяти;
свои снэпшоты;
своя схема фактов;
свой процессный слой;
свой контроль качества;
свой cost control;
своя маршрутизация моделей.
Иначе система будет красивой демкой, но тяжёлой для контроля.

16. Как система “учится”, но без fine-tuning
В production не надо fine-tune после каждой встречи. Это дорого, долго и сложно валидировать.
Вместо этого обучение идёт через:
1. Обновление facts
2. Обновление snapshots
3. Обновление relations
4. Обновление process memory
5. Обновление timelines
6. Обновление retrieval traces
7. Обновление evaluation sets
8. Обновление routing rules

То есть система учится через memory consolidation, а не через постоянное переобучение весов модели.
Fine-tuning можно добавить позже, но только для:
entity extraction
intent classification
company-specific terminology
answer style

А не для хранения фактов.

17. Как выглядит “память компании”
Должно быть несколько уровней.
Level 0. Raw memory
полные встречи
документы
сообщения
таски

Дорого читать, но это источник истины.
Level 1. Chunk memory
чанки + embeddings + metadata

Быстрый поиск по конкретным фрагментам.
Level 2. Fact memory
атомарные утверждения с источниками

Например:
Ингосстрах запросил юридическое согласование Midflow.

Level 3. Entity memory
снэпшоты людей, клиентов, продуктов, процессов

Level 4. Relation memory
кто с чем связан и как

Level 5. Process memory
как идут продажи, внедрение, разработка, согласования

Level 6. Company memory
актуальное понимание компании целиком

Запрос почти никогда не должен идти сразу в Level 0.
Сначала надо идти сверху вниз.

20. Как избегать миллиона токенов на запрос
Нужно использовать context compression.
Перед ответом система собирает не raw chunks, а компактный context pack
{
  "question": "...",
  "intent": "client_status",
  "entities": ["Ингосстрах", "Midflow"],
  "snapshots": [...],
  "facts": [...],
  "relations": [...],
  "timeline": [...],
  "evidence_chunks": [...],
  "uncertainties": [...]
}

Финальная модель получает не 200 чанков, а 10–30 хорошо отобранных элементов.
Context pack должен иметь лимит
fast answer: 4k–8k input tokens
standard answer: 8k–20k
deep answer: 20k–60k
full audit: async / long-running

Даже если модель поддерживает 1M context, это не значит, что надо его использовать. Большой контекст — аварийный режим, не основной.

21. Как выбрать retrieval
Production retrieval должен быть гибридным.
Компоненты retrieval
1. Exact match
имена, даты, клиенты, продукты

2. Keyword search
термины, названия, редкие слова

3. Dense vector search
смысловая близость

4. Sparse vector / BM25
точные формулировки и фразы

5. Graph traversal
связанные сущности

6. Recency boost
свежие данные важнее для статуса

7. Authority boost
решение важнее обсуждения

8. Source type boost
официальный документ важнее случайного комментария

9. Reranking
финальная сортировка кандидатов

Именно hybrid retrieval нужен, потому что dense embeddings хорошо ловят смысл, но могут пропускать точные имена, коды, термины и даты.

22. Скоринг контекста
Каждый найденный элемент получает score:
final_score =
semantic_score * 0.30
+ keyword_score * 0.20
+ graph_relevance * 0.20
+ freshness_score * 0.10
+ authority_score * 0.10
+ user_context_score * 0.05
+ confidence_score * 0.05

Вес можно менять по intent.
Например, для “текущего статуса” freshness важнее.
Для “почему решили” важнее decision authority и timeline.
Для “где говорили” важнее source/chunk match.

23. Как обновлять снэпшоты без хаоса
Нельзя переписывать снэпшот целиком после каждой встречи. Нужно делать patch-based update.
Алгоритм
1. Найти affected entities
2. Для каждой сущности достать текущий snapshot
3. Достать новые факты
4. Сравнить old vs new
5. Сформировать patch
6. Проверить patch
7. Применить patch
8. Сохранить snapshot_version
9. Сохранить memory_event

Snapshot patch
{
  "entity": "Ингосстрах",
  "changes": [
    {
      "field": "current_status",
      "old": "интерес к продукту",
      "new": "юридическое согласование Midflow",
      "reason": "новая встреча с юристами",
      "evidence": ["source_id", "chunk_id"],
      "confidence": 0.82
    }
  ]
}

Это безопаснее, дешевле и объяснимее.

33. Как бороться с галлюцинациями
На ingestion
LLM не может создать факт без source/chunk reference
LLM не может обновить snapshot без evidence
LLM не может удалить старый факт, только пометить outdated

На answer
ответ строится только из retrieved context
факты и выводы разделяются
нет источника — ниже confidence
есть конфликт — показать конфликт
нет данных — сказать, что данных нет


34. Как сделать answer verifier
После генерации ответа запускается лёгкий verifier.
Он проверяет:
1. Все важные утверждения опираются на context?
2. Нет ли утверждений без источников?
3. Не перепутаны ли сущности?
4. Не использованы ли устаревшие данные как актуальные?
5. Не нужен ли deeper search?

Если verifier не уверен:
- либо углубить поиск
- либо пометить answer confidence ниже
- либо вернуть “данных недостаточно”

47. Детальный алгоритм поиска
function answer(question, user, tenant):

1. auth_context = load_permissions(user, tenant)

2. q = normalize(question)

3. intent = classify_intent(q)
   - fact
   - status
   - history
   - comparison
   - process
   - risk
   - decision
   - behavior
   - source_lookup
   - deep_analysis

4. entities = detect_entities(q)
   - exact match aliases
   - fuzzy match
   - LLM only if uncertain

5. company_context = load_cached_company_context(tenant)

6. candidate_entities = resolve_entities(entities, company_context)

7. plan = build_retrieval_plan(intent, candidate_entities)

8. retrieve structured memory:
   - snapshots
   - facts
   - relations
   - process instances
   - timeline

9. check sufficiency

10. if not sufficient:
    retrieve chunks from vector/search index
    filtered by tenant, permissions, entities, dates, source types

11. rerank

12. build context_pack

13. generate answer

14. verify answer

15. return answer + evidence + confidence

16. save query_trace
