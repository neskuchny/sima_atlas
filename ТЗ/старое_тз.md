# Sima Atlas — структура системы

## 0. Что мы собираем (одной фразой)

Надстройку над Cursor / Claude Code / Codex, которая:
1) во время диалога с ИИ **на лету строит визуальную схему продукта** (слои, блоки, связи, статусы, MVP, KPI),
2) хранит её как **живую обновляемую память** (снэпшоты + граф + векторы + история),
3) **подсасывает только нужный кусок этой памяти** в каждый запрос к coding-агенту, чтобы он не галлюцинировал и не жёг токены,
4) автоматически генерирует **ТЗ, Roadmap, вики, документацию, обучающие материалы**.

  └─ subschema_id (рекурсия)

## 5. Что специфично возьмём из Cursor SDK

- `Agent.create({ apiKey, model, local|cloud })` — единый интерфейс к локальному курсору и облачному агенту → один и тот же API из Симы.
- `run.stream()` + `onDelta` — ловим `text-delta`, `thinking-delta`, `tool_call` и в реальном времени обновляем блок на канвасе (вспышка «модуль пишется»).
- **`.cursor/hooks.json`** в корне проекта пользователя — Сима его **генерирует** автоматически, прописывая хуки `beforeShellExecution`, `afterFileEdit`, `stop`, чтобы каждое изменение кода → событие → patch снэпшота блока.
- `agents: { "schema-writer": ..., "verifier": ..., "researcher": ... }` — субагенты, описанные в ТЗ как «отдельный агент-помощник», задаются прямо в SDK.
- MCP-серверы Cursor → подключаем сам Sima Atlas как MCP, чтобы Cursor мог напрямую читать карту и историю.

## 6. CodeWiki-стиль авто-вики (поверх схемы)

Вики собирается **из снэпшотов** триггером `wiki-builder` субагента:

```
/wiki/
  index.md            ← из U-снэпшота: миссия, цель, KPI всего продукта
  architecture/       ← из всех Layer + Block.axis
    overview.mmd      ← Mermaid-диаграмма (блок=node, связь=edge)
    layer-front.md
    layer-backend.md
    ...
  modules/            ← одна страница на блок
    {block_id}.md     ← axis + character.summary + KPI + чек-листы +
                        зависимости + tasks + screenshots + links to code
  data-flow.mmd       ← на основе Link.type=data
  user-paths.mmd      ← на основе Link.type=path
  glossary.md         ← из concept_crystallizer
  history/            ← из SnapshotVersion: changelog, что и почему
  roadmap.md          ← из tasks + status + mvp флагов
  decisions/          ← ADR, из Fact с типом decision
  failures.md         ← из Pattern с negative outcome (опыт неудач)
```

Каждая страница ссылается на конкретные source_id (встречи / ответы ИИ) — то самое «трассировка до источника» из `снепшоты/продакшен.md` §32–34.

## 9. Ключевые архитектурные решения, прямо из источников

1. **Информация течёт outside-in** (`agi_small/README.md`): новые ответы ИИ → Memory; затвердевают → Character; редко → Axis. То есть миссия и KPI блока (Axis) защищены от шума.
2. **Никогда не переписываем снэпшот целиком** — только patch со списком изменений и evidence (`снепшоты/продакшен.md` §23).
3. **Дешёвые операции — в БД и графе, дорогие (LLM) — точечно** (`снепшоты/продакшен.md` §2). Чтение/обход схемы — без LLM. LLM только: extract → patch → answer.
4. **10 готовых маршрутов поиска** + гибкая стратегия — из `снепшоты/концепция.md`. Простой вопрос по блоку = один снэпшот; «как менялся продукт» = snapshot_versions; «почему это решили» = facts+timeline.
5. **Универсальное ядро + доменные адаптеры** (`снепшоты/униварсальная.md`): схема одна, но домен `coding` имеет специфику (Block.frontend, Block.backend, Block.tasks, Block.checks).
6. **Каждое изменение кода — Signal** на инвариант блока. Накопленный стресс ≥ threshold → авто-уведомление «модуль рассинхронизирован с миссией» (`core/axis.py:add_signal, update_needed`).
7. **Hooks Cursor генерируем мы** — пользователю не надо ничего настраивать; Сима кладёт `.cursor/hooks.json` в проект и через них перехватывает каждое file edit / shell execution.
